# 2026-11-07

## v2.7.4：修复 v2.7.2 引入的黑屏无限重启（严重回归）

### 现象
用户 Mac 用 esptool 烧 ota/bilimouse.bin → 屏幕全黑 + 不停重启。
二分对照：烧 v2.7.1 的 app 正常 → 锁定 2.7.2 回归。

### 根因（唯一）：`trans_queue_depth = 0`
v2.7.2 为了修电台页撕裂花屏，把 `bsp_lcd.c` 的 `trans_queue_depth` 从 10 改成 0，
注释写的是「0 = 同步发送」。**这是错的：ESP-IDF 里 0 是非法值，没有"同步模式"语义。**

`esp_lcd_panel_io_spi.c:365`：
```c
if (spi_panel_io->num_trans_inflight < spi_panel_io->queue_size) {
    lcd_trans = &spi_panel_io->trans_pool[spi_panel_io->num_trans_inflight];
} else {
    ret = spi_device_get_trans_result(spi_panel_io->spi_dev, &spi_trans, portMAX_DELAY);
}
```
queue_size=0 时判断恒假 → 首次刷屏走 else → 等一个根本不存在的传输 → **portMAX_DELAY 永久阻塞**
→ app_main 卡死 → 看门狗复位 → 黑屏 + 无限重启。一帧都没发出去，所以屏幕完全无反应。

### 正确值 = 1
=1 时第二次调用必然 `1 < 1` 为假 → 走 else 等上一次传完才入队 → 天然同步，只占 1 个 descriptor，
同时避免 >1 时帧缓冲被改写导致的撕裂。已加 `LCD_IO_QUEUE_DEPTH` 宏 + `_Static_assert(>=1)`。

### 教训
- **esp_lcd SPI 的 `trans_queue_depth` 只能是 ≥1；1 才是串行/同步，0 会死锁。**
- v2.7.2 是「用户已拔 USB、只能编译验证」的情况下发的，**改显示/驱动层参数必须真机验证**，
  编译器不会拦这种运行时死锁。
- 用户 Mac 上二分对照（烧旧版 app 到 0x20000 + 清 otadata）是定位回归最快的手段。

### 顺带修好的烧录问题
仓库原来只有 app 镜像，用户 esptool 写 0x0 会砸掉 bootloader → 黑屏且无串口。
现在 `ota/factory/{bootloader,partition-table,ota_data_initial}.bin` 常驻仓库，
release.py 每次发版自动同步；README 加了 macOS/Linux 完整烧录命令。
正确偏移：0x0 / 0x8000 / 0x10000 / **0x20000(app)**。
开了 `BOOTLOADER_APP_ROLLBACK_ENABLE`，重烧 app 时最好连 0x10000 的 otadata 一起清，
否则可能被回滚到空的 ota_1。

## v2.7.5 / v2.7.6：OTA 检查卡死 + macOS 点击失效

### 「检查更新一直卡着」的根因与对策
不是死锁，是**单源 + 长超时**：manifest 只有
`github.com/.../releases/latest/download/manifest.json` 一个地址，302 到
`objects.githubusercontent.com`；国内 DPI/DNS 环境下这个域名常常不返回 RST
而是直接黑洞（连接挂着不动），要等满 8~10s 超时才算失败，再重试 3 次 = 最长 60s
屏幕一动不动（屏上只有一句「获取中…」，看不出在动）。
对策（v2.7.5/2.7.6）：
- manifest 改多源串行，每源 5s(resolve)/7s(fetch)，屏上显示「获取中…(2/4)」：
  raw 直连 → **gh-proxy.com 反代** → jsDelivr → releases 固定链接。
- bin 也走候选：manifest.url → `https://gh-proxy.com/<manifest.url>` → jsDelivr@版本号。
- 单源重试 3→2 次；检查结论出来立刻放开 s_task_busy，蓝牙恢复/WiFi 重连移到收尾
  且用 s_wifi_quiet 避免把「已是最新」刷成「正在连 xxx」。

**镜像实测（2026-11-07，本机）**：
- `raw.githubusercontent.com` 直连 OK；`gh-proxy.com/<raw url>` 1.9MB/0.9s（最可靠）
- `cdn.jsdelivr.net/gh/...@master/...` 200 但**内容滞后**（仍返回 2.7.4）；
  按 commit 取 `@b48c05f/...` 立刻 200 —— jsDelivr 的 branch/tag 引用有缓存，
  发版后短时间内读不到新版本，只能当最后兜底。
- `raw.gitmirror.com` 解析失败、`ghproxy.net` 20s 超时，都不可用。

### macOS 点击/双击/右键失效（用户贴来的分析，逐条核对后采纳 6 条）
1. **AUTH_CMPL 后补 `s_report_enabled=true`**（真因）：绑定设备重连时主机不重写 CCCD，
   is_ready() 恒假 → click/move 全部在入口 return，但屏幕已显示「已就绪」。
2. **`esp_ble_gap_set_prefer_conn_params` 是无效 API**：它只写 PPCP 特征值，不会对已连链路
   发起更新。改 `esp_ble_gap_update_conn_params`，在 AUTH_CMPL 后发，15~30ms、latency 0
   （Apple 指南：min≥15ms、max≥min+15ms；**latency 必须 0**，贴来的文档建议 latency=4
   是错的，跳过事件会让 down/up 被折叠成一次)。
3. **click 120ms → 45ms**：120ms 把两次点击的节奏拉到 350ms+，macOS 判成两次独立单击，
   双击永远出不来。同时按下期间同步 s_btn_mask，并用 s_click_busy 在点击窗口内丢弃位移
   （混一帧 dx≠0 就变拖拽）。
4. Appearance `0x03C0(Generic HID)` → `0x03C2(Mouse)`，广播 adv_data 与
   esp_ble_gap_config_local_icon 两处都要改。
5. Mouse/Key CCCD 权限补 ENCRYPTED（与 Consumer 一致），否则 macOS 质疑设备安全性。
6. `hid_add_id_tbl()` 里 mouse 的 `cccdHandle` 误用 `..._MOUSE_IN_VAL` → 改 `..._MOUSE_IN_CCC`（笔误）。
未采纳：Ctrl+左键模拟右键（代码里早已改原生 0x02，文档这段是旧信息）；
把 `esp_ble_set_encryption(NO_MITM)` 改掉（当前配对是通的，动它风险大于收益）。
