## OTA / 内存 / 电台 收尾（v2.6.1 → v2.7.1，全部实机验证）

### 四个原始 bug 的最终根因与修复
1. **电台列表为空**：既有多源列表兜底（内置 3 个 CNR 台 + raw.githubusercontent 7 台）。
   运行期 TLS 拉列表失败的真正原因是 **esp-aes 需要内部 DMA 缓冲**
   （`esp-aes: Failed to allocate memory` → tls read -0x84），
   WiFi+蓝牙常驻后内部只剩 4KB。→ 关闭 `CONFIG_MBEDTLS_HARDWARE_AES`（改软件 AES）。
2. **点「开始检查更新」没反应**：两层原因
   a) 9KB 任务栈分配失败（内部 RAM 不足）→ **BLE 挂起/恢复**（hid_ble_suspend/resume，
      suspend 时先 esp_hidd_profile_deinit，官方 demo 的 deinit 漏清 enabled 标志已修）；
      恢复前必须 `esp_wifi_disconnect()`，否则连接态动态缓冲把刚还的内存切碎，
      Bluedroid 的 future_new assert 崩溃重启。
   b) `ota_download_run()` 守卫要求 `phase==READY`，而 `ota_update_download()`
      起任务前已把 phase 置成 DOWNLOAD → 永远失败（"download without a READY check"）。
3. **统一左上角返回**：ui.c draw_header 统一「< 返回」胶囊（BACK_W=58），删台列表底部返回按钮。
4. **首页底部文字 + 图标居中**：HOME 模式不画 footer，HOME_TILE_Y=(240-96)/2=72。

### 关键教训（会再踩）
- `esp_http_client_get_header()` 读的是**请求头**，响应头默认不保存！
  跟随 302 必须用 `esp_http_client_set_redirection()` + `esp_http_client_get_url()`。
- GitHub releases CDN（Azure Front Door）对 ESP-IDF TLS 指纹有 bot 防护，
  间歇/持续返回 **618 + XHTML**（PC curl 200）。→ OTA 资产必须走
  **raw.githubusercontent.com**（radio 同源，从未失败）：`ota/manifest.json`
  固定入口 + manifest.url 指向 tag 化 bin 路径。release.py 已双通道发布。
- **release.py 必须 `env.pop("MSYSTEM")`**：Git Bash 下 idf.py 打印 MSys 警告后
  以 0 退出但**不编译**，导致 2.6.5/2.6.6 连发两版旧 bin。现已加防护：
  编译后校验 bin 内含目标版本号，否则退出。
- LCD 整帧 `draw_bitmap` 不可行：spicommon 每次传输临时 malloc 内部对齐缓冲，
  150KB 分配必失败（`spicommon_dma_setup_priv_buffer Failed`，画面卡住）。
  → ui.c 改 **4 行分条刷屏**（2560B/条）。
- 电台 8K/10K 任务栈 + PCM 缓冲全部改 PSRAM（`xTaskCreateWithCaps`），
  内部 RAM 只剩 4KB 最大块时内部栈永远分配不出来。
- 只烧 `0x20000` 不会生效：OTA 后 otadata 指向 ota_1，直烧要连
  `ota_data_initial.bin` 一起写（或全量四件套）。

### 版本现状
- 设备 = v2.7.1 = 线上 latest（releases + raw 双通道一致）。
- 端到端验证：2.6.9 → check → 下载 1.9MB（42s）→ 安装 → 重启 → 2.7.0；
  2.7.1 上 check 显示「已是最新」、BLE resume 正常、7 台列表 3s 拉完。

## v2.7.2：第二轮 bug 修复（用户已拔 USB，无法串口实测，仅编译验证 + OTA 发布）

### 根因清单
1. **电台页花屏**：`bsp_lcd.c` 的 `trans_queue_depth=10` 让 esp_lcd 走 SPI 异步队列，
   draw_bitmap 立即返回而 DMA 还在后台读帧缓冲，下一帧重绘改写在传数据 → 撕裂。
   → 改 0（同步），每条 4 行仅 ~100us 阻塞。**教训：esp_lcd SPI 面板 trans_queue_depth>0 = 异步！**
2. **电台不能播 / "可能不是 MP3 编码"**：CNR 的 m3u8 是 **AAC**，Helix 只解 MP3 → 死循环找帧。
   → 全部换成实测 audio/mpeg 的蜻蜓源（radio-browser 数据库找台 + curl 验证 Content-Type）。
   CNR-1 MP3 = https://lhttp.qtfm.cn/live/15318317/64k.mp3。
3. **选台跳回电台主页**：PICK 处理里 ui_set_mode(UI_MODE_RADIO) 是有意为之但体验差 → 留在列表页。
4. **"点击/已执行"乱入**：触摸任务里"空白轻点=主机左键"全模式生效 → 电台/红外页误触刷卡片。
   → 新增 ui_mode_uses_pointer_click()，仅 REMOTE/MOUSE 生效。
5. **红外学习"不能用"**：xTaskCreate(4KB 内部栈) 静默失败（内部 RAM 只剩 4KB 最大块）。
   → 6KB + 4KB 回退 + 失败屏显。栈不能放 PSRAM：bank_save 写 NVS 时 cache 挂起会崩。
6. MP3 直连 timeout 1s→3s（qtfm TLS 握手超 1s 会"连接失败"）。
7. 播放前强制 ota_update_wifi_online()（幂等）。
8. radio/radio_stations.json 改 9 个 MP3 台（在线拉取，无需 OTA 即生效）。

发布：v2.7.2（releases + raw 双通道，bin 版本校验通过 1921952B）。

## WiFi 备用热点连不上（代码已改，未发版）

排查 ota_update.c 的多凭据逻辑，确认 5 个缺陷：
1. `wifi_try_cred` 换凭据时**没有 esp_wifi_disconnect()**，旧 AP 的 connect 流程还在跑，
   新的 set_config 后 `esp_wifi_connect()` 返回 ERR_WIFI_CONN（被忽略）→ 新 SSID 一次 probe 都没发出。
2. 断线回调无条件 `esp_wifi_connect()`，与换凭据抢同一个 STA。→ 加 `s_cred_switching` 闸门。
3. 单个凭据只 connect 一次、9s 判死（ESP-IDF 不会自动重连）→ 改成 2 轮 × 4.5s。
4. `wifi_config_t wc={0}` 使 `pmf_cfg.capable=false`，现代 AP/手机热点（WPA3/强制 802.11w）直接拒关联。
   → capable=true + required=false + sae_pwe_h2e=BOTH。
5. `wifi_cred_t list[3]` + `creds_collect(list,3)`：用过 `wifi set` 后 NVS 占一个槽，
   第三个编译期默认热点被挤出列表，永远不尝试 → 槽位改 4。

新增诊断（串口）：`wifi scan`（列出 SSID/CH/RSSI/AUTH，判定「扫不到」还是「认证失败」）、
`wifi clear`（清 NVS 回落默认）、断线日志打印 reason 码 + 中文解释（201=扫不到/202=密码错/203=需 PMF）、
`creds_dump()` 打印 SSID 的 hex 字节（抓中文乱码/尾随空格）。

待判定：`Grey Shanghai` 若是 WPA2-Enterprise(802.1X)，PSK 方式永远连不上，需另加 esp_wifi_sta_wpa2_ent_*。
ESP32-S3 只有 2.4GHz，5G-only SSID 必然 reason=201。
